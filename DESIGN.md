# Bug Radar — сервис аналитики инцидентов

Дашборд для еженедельного разбора клиентских инцидентов из Jira.
Главный сценарий: понедельник, 30 минут, команда смотрит на один экран и знает,
что обсуждать.

---

## 0. Что решаем и чем это отличается от доски Jira

Доска Jira отвечает на вопрос «какие задачи есть». Разбор инцидентов требует ответов на другие:

| Вопрос команды | Метрика |
|---|---|
| Нас заливает или мы справляемся? | приток vs разбор за период, net flow |
| Мы быстро реагируем? | время до взятия в работу (p50/p85) |
| Клиент долго ждёт разблокировки? | время до даты исправления |
| Что горит прямо сейчас? | открытые с высоким рангом и большим возрастом |
| Стало лучше, чем неделю назад? | сравнение с предыдущим периодом |

Отсюда три принципа, которые определяют весь дизайн:

1. **Инцидент считается решённым в момент снятия блокера у клиента**, а не в момент
   закрытия задачи. `Дата исправления` — первоклассное поле, а не примечание.
2. **Метрики времени считаются только по завершённым инцидентам.** Средняя по открытым
   занижена систематически: чем дольше живёт инцидент, тем меньше шансов, что он уже
   попал в среднее. Возраст открытых — отдельная метрика, рядом, но никогда не в одной сумме.
3. **Любое число кликабельно** и разворачивается в список конкретных инцидентов со
   ссылками в Jira. Число без возможности провалиться на митинге бесполезно: спор
   «а что это за 14 штук» съедает половину встречи.

## 1. Архитектура

### 1.1 Два контура, один фронтенд

Прямое обращение из браузера к Jira Cloud невозможно: она не отдаёт CORS-заголовки
для авторизованных запросов, а API-токен в `localStorage` статической страницы — это
токен с полными правами учётки в открытом виде (тот же вывод, что в `sprint-progress`).
Поэтому источников данных два, и фронтенд не знает, какой из них активен.

```
                    ┌───────────────────────────────┐
   CSV из Jira ────►│  CsvSource   ──┐               │
                    │                ├─► нормализация│
   bug-radar-proxy ►│  ApiSource   ──┘   в единую    │
        │           │                    модель      │
        │           │            IncidentStore       │
        │           │                  │             │
        │           │            Metrics (чистые ф-ии)│
        │           │                  │             │
        │           │            Charts / UI          │
        │           └───────────────────────────────┘
        │
        ▼
   Jira REST API (токен живёт только на сервере)
```

**Контур A — CSV (работает в день ноль, инфраструктура не нужна).**
Выгрузка из Jira по JQL → Export CSV → перетащили в приложение. Ровно то, что уже
отлажено в `sprint-progress`: автораспознавание колонок, словарь статусов, повторная
заливка обновляет, а не задваивает.

**Контур B — прокси (нужен для живых данных и для истории переходов).**
`bug-radar-proxy` — тонкий Node-сервис: держит токен у себя, ходит в Jira, нормализует,
кеширует, отдаёт фронтенду `GET /api/incidents?from&to`. Разворачивается в Docker
внутри периметра.

**Что даёт только контур B, и это важно при планировании этапов:**
плоский CSV не содержит истории переходов. Значит, `время до взятия в работу`
из CSV не посчитать — если только в проекте нет отдельного кастомного поля с датой
взятия в работу. Пока прокси нет, эта метрика показывается как «нет данных»,
а не подменяется догадкой.

### 1.2 Нормализованная модель инцидента

Единственная структура, с которой работают метрики. Оба источника приводятся к ней.

```js
{
  key: 'SUP-1423',
  summary: 'Не грузится отчёт по продажам',
  type: 'Defect',
  status: 'In Progress',
  statusCategory: 'indeterminate',   // new | indeterminate | done
  rank: 78,                          // 0..100, кастомное поле
  assignee: 'Марат',
  components: ['Reports'],
  labels: ['customer-blocker'],
  reporter: 'support-bot',
  customer: 'ООО Ромашка',           // опционально, если поле есть

  createdAt:  '2026-08-24T09:12:00+05:00',
  startedAt:  '2026-08-24T14:40:00+05:00', // первый переход в In Progress (changelog)
  fixedAt:    '2026-08-26T18:02:00+05:00', // кастомное поле «Дата исправления»
  resolvedAt: null,                        // resolutiondate — закрытие в Jira

  reopenCount: 0,
  lastActivityAt: '2026-08-27T10:00:00+05:00',
  history: [ { at, field, from, to } ]      // из changelog, для таймлайна и «состояния на дату»
}
```

Производные поля считаются один раз при загрузке:

```js
unblockedAt = min(fixedAt, resolvedAt)        // момент, когда клиент разблокирован
timeToStart = startedAt - createdAt           // null, если не начинали
timeToFix   = unblockedAt - createdAt         // null, если ещё не разблокирован
timeToClose = resolvedAt - createdAt          // null, если не закрыт
age         = now - createdAt                 // только для открытых
isOpen      = unblockedAt === null
```

Правило `min(fixedAt, resolvedAt)` неочевидно, но важно: если инцидент закрыли, забыв
проставить дату исправления, он всё равно должен попасть в «разобранные» — иначе метрика
наказывает команду за аккуратность заполнения полей. И наоборот: если дата исправления
проставлена раньше закрытия, для клиента блокер снят именно тогда.

### 1.3 Окно запроса ≠ окно отображения

Ключевое архитектурное следствие метрики «открытых на конец периода»: чтобы её посчитать,
нужны не только инциденты за период, но и всё, что открыто с любого момента в прошлом.

JQL, который тянет прокси:

```
project = SUP AND type = Defect AND (
     created >= "{from}"
  OR resolutiondate >= "{from}"
  OR "Дата исправления" >= "{from}"
  OR statusCategory != Done
)
```

Последнее условие — незакрытый хвост любой давности. Без него график backlog врёт.

### 1.4 Кеш и обновление

- Полная синхронизация при первом запуске, дальше инкремент по `updated >= lastSync`.
- Кеш прокси — SQLite (или JSON-файл на диске для совсем простого деплоя):
  таблица `incidents` + таблица `changelog`. Jira опрашивается, а не наоборот — вебхуки
  не нужны и требуют белого IP.
- Кнопка «Обновить» + фоновый рефреш раз в N минут (по умолчанию 15).
- **Фиксация недели.** По кнопке состояние периода сохраняется снапшотом (JSON).
  Числа на митинге не меняются под руками, а через месяц можно открыть ту же неделю
  и увидеть ровно то, что обсуждали. Это же даёт честную историю по неделям без
  пересчёта задним числом.

### 1.5 Безопасность

- Токен Jira — только в env прокси, только read-only учётка.
- Прокси не проксирует произвольный JQL от клиента: набор запросов зашит, клиент
  передаёт только период и фильтры. Иначе внутренний дашборд превращается в
  универсальный ридер чужих проектов.
- CORS прокси ограничен origin дашборда.

## 2. Структура экранов

### 2.1 `Weekly` — главный экран, режим митинга

Открывается по умолчанию, период — прошедшая неделя. Помещается в один экран проектора,
читается с задних рядов.

```
┌──────────────────────────────────────────────────────────────────────────┐
│  Bug Radar        [ Неделя ▾ 25 авг — 31 авг ]   [Обновить] [Сводка] [⚙] │
├──────────────────────────────────────────────────────────────────────────┤
│  ┌──────────┐ ┌──────────┐ ┌──────────┐ ┌──────────┐ ┌──────────┐        │
│  │ Пришло   │ │ Разобрано│ │ Закрыто  │ │ Открыто  │ │ Просроч. │        │
│  │   14     │ │   11     │ │    8     │ │   23     │ │    5     │        │
│  │ +3 к пр. │ │ −2       │ │ +1       │ │ +3       │ │ +2       │        │
│  └──────────┘ └──────────┘ └──────────┘ └──────────┘ └──────────┘        │
│  ┌────────────────────────┐ ┌────────────────────────┐                   │
│  │ До взятия в работу     │ │ До исправления         │                   │
│  │ 3.2 ч  p85 9.1 ч       │ │ 2.1 дн  p85 6.4 дн     │                   │
│  └────────────────────────┘ └────────────────────────┘                   │
├──────────────────────────────────────────────────────────────────────────┤
│  Поток за 8 недель                    │  Открытые по рангу               │
│  ▁▃▅▂▆▄▃▅  приток / разбор + backlog  │  ███ 90+ (3)  ██ 70+ (7) ...     │
├──────────────────────────────────────────────────────────────────────────┤
│  Требуют обсуждения (6)                                                   │
│  SUP-1201  92  17 дн  Оплата не проходит у 3 клиентов     Марат   ⚠      │
│  SUP-1188  85  12 дн  Экспорт падает на больших отчётах   —       ⚠      │
├──────────────────────────────────────────────────────────────────────────┤
│  Пришло на этой неделе (14)  ·  Разобрано (11)  ·  Всё ещё открыто (23)   │
└──────────────────────────────────────────────────────────────────────────┘
```

Блок «Требуют обсуждения» — это и есть повестка встречи, собранная автоматически:
высокий ранг + возраст выше SLA, без исполнителя, без движения N дней, переоткрытые.
Отсортировано по «стоимости»: `ранг × возраст`.

### 2.2 `Explore` — гибкая аналитика

Произвольный период, все фильтры, все графики: динамика по дням/неделям, распределение
по рангам, heatmap времени жизни, воронка, разрезы по исполнителю и компоненту.
Пресеты фильтров сохраняются и переключаются одним кликом.

### 2.3 `Incidents` — таблица

Колонки: `Key · Ранг · Summary · Создан · В работе · Исправлен · Закрыт · До работы ·
Жизнь · Статус · Исполнитель`. Сортировка по любой, фильтр сверху, экспорт CSV.
Подсветка строк: красная левая граница — просрочен по SLA своего ранга, янтарная —
подходит к сроку, серый текст — разобран.

Таблица — это ещё и цель всех drill-down: клик по KPI-карточке, сегменту графика или
ячейке heatmap открывает её же с предзаполненным фильтром и заголовком
«Открытые ранга 70+ старше 7 дней — 5».

### 2.4 `Incident` — панель детали (drawer справа)

Таймлайн из changelog: создан → взят в работу → переходы → исправлен → закрыт,
с интервалами между вехами. Ссылка в Jira, локальная заметка команды
(живёт в bug-radar, в Jira не уезжает).

### 2.5 `Trends` — история по неделям

Таблица недель (пришло / разобрано / закрыто / медиана жизни / backlog на конец) и
график тех же рядов. Источник — зафиксированные снапшоты, поэтому история не переписывается.

### 2.6 `Settings`

Подключение (URL, JQL, режим CSV/API), маппинг полей — включая `Дата исправления` и
`Ранг` (см. §7), границы ранговых полос, SLA по полосам, порог «висит дольше X дней»,
порог «без движения», тема.

## 3. Метрики и формулы

Обозначения: период `[F, T]`, набор инцидентов после фильтра ранга `I = { i : rank(i) ≥ R }`
(по умолчанию `R = 30`).

### 3.1 Ранг: настраиваемое и необязательное измерение

Ранг — не обязательное поле и не константа в коде. Порог задаётся в настройках,
а инциденты без ранга обрабатываются по явно выбранному правилу.

```js
settings.rank = {
  field: 'customfield_10042' | null,  // null — в проекте ранга нет вообще
  min: 30,                            // порог; 0 или null — не фильтруем
  missing: 'exclude',                 // 'exclude' | 'include' | 'only'
  bands: [                            // границы редактируются, полос может быть меньше
    { from: 90, label: 'критический', color: 'var(--rank-critical)' },
    { from: 70, label: 'высокий',     color: 'var(--rank-high)' },
    { from: 50, label: 'средний',     color: 'var(--rank-medium)' },
    { from: 30, label: 'низкий',      color: 'var(--rank-low)' },
  ],
}
```

```
I = { i ∈ all :
        (rank.min == null)                    → true
      ∨ (i.rank == null)                      → rank.missing == 'include'
      ∨ (i.rank ≥ rank.min) }
```

Три режима для инцидентов без ранга нужны потому, что «нет ранга» означает разное
в разных командах: у одних это ещё не оценённый свежий инцидент (его нельзя терять,
`include`), у других — мусор из автоматических интеграций (`exclude`). Режим `only`
существует для одной задачи — открыть список неоценённых и проставить ранги.

Что бы ни было выбрано, **счётчик «без ранга: N» показан рядом с фильтром всегда** и
кликабелен. Тихо выкидывать часть выборки нельзя: пропавшие инциденты обнаружатся
на митинге в самый неудобный момент.

Порог живёт в шапке экрана как быстрый переключатель `≥30 · ≥50 · ≥70 · все`, а не
только в настройках: на разборе регулярно нужно за секунду посмотреть «а если считать
всё подряд». Пресеты фильтров сохраняют порог вместе с остальными условиями.

**Ранга может не быть вовсе.** Если `rank.field == null`, приложение работает без него:
ранговые полосы схлопываются в одну строку «все инциденты», SLA берётся единый из
`sla.default`, в таблице нет колонки `Ранг`, а сортировка «Требуют обсуждения» падает
на `age` (см. §3.8). Ни одна метрика §3.2–3.7 ранга не требует — он везде только фильтр
и разрез. Это осознанное ограничение: ранг задаёт приоритеты, но не должен быть
условием запуска сервиса.

Ранг меняется со временем. Фильтруем по **текущему** значению, и это написано подписью
под фильтром; исторический ранг на момент `T` восстанавливается из changelog (этап 4).

### 3.2 Счётные метрики периода

```
Created(F,T)  = |{ i ∈ I : F ≤ i.createdAt  ≤ T }|
Fixed(F,T)    = |{ i ∈ I : F ≤ i.unblockedAt ≤ T }|      // блокер снят у клиента
Closed(F,T)   = |{ i ∈ I : F ≤ i.resolvedAt  ≤ T }|      // закрыто в Jira
FixedNotClosed(F,T) = |{ i : F ≤ i.fixedAt ≤ T ∧ i.resolvedAt == null }|
NetFlow(F,T)  = Created − Fixed                          // > 0 — очередь растёт
FlowRatio     = Fixed / Created                          // ≥ 1 — справляемся
```

`Created`, `Fixed` и `Closed` — три разные когорты. Делить `Closed / Created`
за один период и называть это «процентом закрытия» нельзя: в числителе и знаменателе
разные множества инцидентов. Для доли решённого есть когортная метрика (§3.5).

### 3.3 Открытые на дату

```
OpenAt(D) = |{ i ∈ I : i.createdAt ≤ D ∧ (i.unblockedAt == null ∨ i.unblockedAt > D) }|
```

Считается из полной выборки (§1.3), а не из инцидентов периода. Разбивка по ранговым
полосам: `OpenAt(T)` по каждой из 30–49 / 50–69 / 70–89 / 90–100.

```
Aging(X) = |{ i : isOpen(i) ∧ age(i) > X дней }|
```

### 3.4 Метрики времени

Считаются **только по завершённым** — по инцидентам, у которых соответствующая веха
наступила внутри периода.

```
TTS = { i.startedAt − i.createdAt     : i.startedAt ∈ [F,T] }   // до взятия в работу
TTF = { i.unblockedAt − i.createdAt   : i.unblockedAt ∈ [F,T] } // до снятия блокера
TTC = { i.resolvedAt − i.createdAt    : i.resolvedAt ∈ [F,T] }  // до закрытия
```

Для каждого набора показываем **медиану крупно и p85 рядом**, среднее — в подсказке.
Причина: распределение времени жизни всегда с тяжёлым хвостом, один инцидент,
провисевший три месяца, поднимает среднее так, что метрика перестаёт реагировать
на реальные изменения. p85 отвечает на вопрос «сколько ждёт почти любой клиент»,
и именно он выносится в SLA.

Перцентиль — методом ближайшего ранга (без интерполяции, чтобы результат всегда
совпадал с реальным инцидентом, на который можно ткнуть):

```js
function percentile(sorted, p) {
  if (!sorted.length) return null;
  const idx = Math.ceil(p * sorted.length) - 1;
  return sorted[Math.min(Math.max(idx, 0), sorted.length - 1)];
}
```

Отдельно, никогда не в одном числе с предыдущими:

```
AgeOpen = { now − i.createdAt : isOpen(i) }   // медиана и максимум возраста открытых
```

Опция «рабочий календарь» (5×8): интервалы считаются без выходных и ночей. По умолчанию
выключено, потому что клиент ждёт по календарным часам; включается для честной оценки
реакции команды.

### 3.5 Когортные метрики

Когорта — инциденты, созданные в периоде. Отвечает на вопрос «что стало с тем,
что пришло на этой неделе».

```
C = { i ∈ I : i.createdAt ∈ [F,T] }
Started(C)   = |{ i ∈ C : i.startedAt ≠ null }|
Fixed(C)     = |{ i ∈ C : i.unblockedAt ≠ null }|
Closed(C)    = |{ i ∈ C : i.resolvedAt ≠ null }|
ResolutionRate = Fixed(C) / |C|
```

Это же — воронка `Created → In Progress → Fixed → Closed`: четыре ступени по одной
когорте, с конверсией и медианным временем между ступенями. Воронка, построенная
на смешанных когортах, показывает конверсии больше 100% и дискредитирует весь дашборд.

### 3.6 SLA и «просрочено»

Порог на ранговую полосу, две метрики на каждую. Полосы и значения редактируются;
если ранга в проекте нет — действует единый `sla.default`:

| Полоса | До взятия в работу | До исправления |
|---|---|---|
| 90–100 критический | 1 ч | 1 день |
| 70–89 высокий | 4 ч | 3 дня |
| 50–69 средний | 1 день | 7 дней |
| 30–49 низкий | 2 дня | 14 дней |

```
overdue(i)  = isOpen(i) ∧ age(i) > sla.fix[band(i)]
atRisk(i)   = isOpen(i) ∧ age(i) > 0.8 × sla.fix[band(i)]
SlaMet(F,T) = |{ i : i.unblockedAt ∈ [F,T] ∧ timeToFix(i) ≤ sla.fix[band(i)] }| / Fixed(F,T)
```

Отсюда берутся цвета: зелёный — в норме, янтарный — `atRisk`, красный — `overdue`.
Цвет в интерфейсе не назначается «на глаз», он всегда следствие порога, который
команда сама задала в настройках.

### 3.7 Сравнение с предыдущим периодом

Предыдущий период — той же длины, вплотную: `[F − (T−F), F)`.

```
delta = current − previous
deltaPct = previous > 0 ? (current − previous) / previous : null
```

Знак дельты и «хорошо/плохо» — разные вещи. У каждой метрики свой `goodDirection`:
рост `Created` — плохо, рост `Fixed` — хорошо, рост медианы времени — плохо. Карточка
красит дельту по `goodDirection`, а не по знаку. Дельта меньше 5% и меньше 2 штук
показывается серым как шум: недельные числа маленькие, и подсвечивать «+1» красным —
способ научить команду игнорировать цвета.

### 3.8 Дополнительные сигналы

```
Reopened(F,T)  = |{ i : есть переход из статуса категории done в периоде }|
Stale(N)       = |{ i : isOpen(i) ∧ now − i.lastActivityAt > N дней }|
Unassigned     = |{ i : isOpen(i) ∧ assignee == null }|
CostRank(i)    = (i.rank ?? 50) × age(i)   // без ранга — сортировка по возрасту
```

## 5. Стек

**Рекомендация: начать с того же zero-build стека, что и `sprint-progress`.**
Аргумент не в идеологии, а в том, что готовы дизайн-система, SVG-графики, загрузчик
тестов и парсер Jira-CSV — MVP собирается из существующего кода, а не с нуля.
Ядро (`metrics.js`) — чистые функции без DOM, поэтому при переезде на React
переносится один в один.

```
bug-radar/
  index.html            каркас, модалки, панели
  css/styles.css        дизайн-система (из sprint-progress + ранги и SLA)
  js/model.js           нормализованная модель, производные поля, localStorage
  js/sources/csv.js     импорт Jira CSV (порт из sprint-progress)
  js/sources/api.js     клиент прокси
  js/metrics.js         все формулы §3 — чистые функции
  js/charts.js          SVG-графики (порт + поток, воронка, heatmap)
  js/filesync.js        автосохранение состояния в файл (File System Access API)
  js/summary.js         текстовая сводка
  js/ui.js, js/app.js   рендер и события
  tests/                node --test, без зависимостей
proxy/
  server.js             fastify: /api/incidents, /api/fields, /api/health
  jira.js               клиент Jira: пагинация, changelog, ретраи
  normalize.js          Jira issue → модель §1.2
  cache.js              SQLite, инкремент по updated
  Dockerfile, .env.example
```

- **Фронтенд:** vanilla ES + CSS-токены, графики свои на SVG. Без сборки, без CDN.
- **Прокси:** Node 20 + Fastify. Кеш — better-sqlite3. Docker-образ, read-only токен в env.
- **Тесты:** `node --test`, покрываются метрики, нормализация, парсер CSV, границы периодов
  и таймзоны. Это та часть, где ошибка не видна глазом и тихо портит цифры на митинге.

**Альтернатива, если сервис будет развивать несколько человек:** Vite + React + TS +
Tailwind + Recharts (или Tremor для готовых KPI-карточек). Даёт типы на модели инцидента
и знакомый большинству стек ценой сборки и ~40 зависимостей. Порог перехода —
примерно 6–8 тысяч строк фронтенда или второй разработчик на постоянке; раньше
сборка стоит дороже, чем экономит.

## 6. План реализации

### Этап 0 — договорённости (полдня, до кода)

Ответы, без которых любой код придётся переписывать:

1. Jira Cloud или Server/DC — от этого зависят эндпоинты и формат дат.
2. `id` кастомного поля «Дата исправления» (`customfield_XXXXX`) — берётся из
   `/rest/api/3/field`.
3. Что такое ранг 0–100: кастомное числовое поле или отображение приоритета?
   Штатный Jira Rank — это LexoRank-строка для сортировки бэклога, число 0–100
   почти наверняка ваше собственное поле, и его нужно назвать явно. Заодно —
   какая доля инцидентов приходит без ранга и что с ними делать по умолчанию.
4. Считается ли «взято в работу» первым переходом в конкретный статус, и в какой.
5. Базовый JQL и границы ранговых полос + стартовые SLA.

### Этап 1 — MVP (≈ неделя)

Цель: следующий понедельник разбираем по дашборду, а не по доске.

- Импорт Jira CSV, нормализация, `localStorage`.
- Настраиваемый фильтр ранга с режимом для инцидентов без ранга (§3.1) — с первого дня,
  включая работу вообще без поля ранга.
- Метрики: `Created`, `Fixed`, `Closed`, `FixedNotClosed`, `OpenAt(T)` с разбивкой по рангу,
  `Aging(X)`, медиана и p85 времени до исправления, сравнение с прошлым периодом.
- Экраны: `Weekly` (KPI + «требуют обсуждения» + поток по дням) и `Incidents` с фильтрами,
  сортировкой и экспортом CSV.
- Drill-down по каждому числу.
- Тесты метрик и границ периодов.

Метрика «до взятия в работу» на этом этапе показывается только если в выгрузке есть
поле с датой начала работы — иначе честное «нет данных, нужен прокси».

### Этап 2 — живые данные (≈ неделя)

- `bug-radar-proxy`: Jira-клиент с пагинацией и ретраями, нормализация, SQLite-кеш,
  инкремент по `updated`, Docker, health-check.
- Changelog → `startedAt`, `reopenCount`, `lastActivityAt`, таймлайн инцидента.
- Кнопка «Обновить» и фоновый рефреш; переключение CSV ↔ API в настройках.
- Метрики TTS, `Reopened`, `Stale`, воронка по когорте.

### Этап 3 — недельный ритуал (≈ неделя)

- Фиксация недели снапшотом и экран `Trends` по неделям.
- Текстовая сводка + горячие клавиши.
- SLA по ранговым полосам, подсветка `overdue`/`atRisk`, метрика `SlaMet`.
- Heatmap возраста, панель детали инцидента, светлая тема.

### Этап 4 — по потребности

- Пресеты фильтров и шаринг вида ссылкой.
- Заметки к инцидентам, разрезы по исполнителю/компоненту/клиенту.
- Рабочий календарь для метрик времени.
- Ранг на момент `T` из changelog вместо текущего.
- Автопост сводки в Slack по расписанию — тогда часть команды может не приходить
  на встречу вовсе, а это лучший исход для еженедельного статуса.

## 7. Риски и краевые случаи

| Риск | Что делаем |
|---|---|
| «Ранг 0–100» окажется не тем полем | выясняем на этапе 0; маппинг полей — в настройках, не в коде |
| Ранга нет или он заполнен через раз | ранг необязателен на всех экранах (§3.1): порог настраиваемый, для инцидентов без ранга — явный режим exclude/include/only и постоянный счётчик рядом с фильтром |
| Даты исправления заполняются нерегулярно | `min(fixedAt, resolvedAt)` + счётчик «закрыто без даты исправления» на видном месте |
| Ранг меняется задним числом | по умолчанию фильтр по текущему рангу, это заявлено в подписи; историчный ранг — этап 4 |
| Таймзоны и границы суток | всё храним в UTC, границы периода режем по таймзоне команды из настроек, тесты на переход через полночь и выходные |
| Лимиты Jira API и пагинация | инкрементальная синхронизация, ретраи с backoff, эндпоинт поиска сверяем с версией инсталляции |
| Маленькие числа и шумные дельты | дельта до 5% и до 2 штук — серая; для трендов смотрим 8 недель, а не неделю к неделе |
| Дашборд превращается в KPI для оценки людей | разрезов по исполнителю нет на главном экране; они есть в `Explore`, но метрики устроены вокруг потока, а не персональной выработки |
